# OPPi Rust Runtime JSON-RPC Contract

Status: experimental Stage 5 contract. This document tracks the Rust-owned `oppi-server --stdio` line-delimited JSON-RPC surface so CLI, Pi-package, and future VS Code clients can evolve against the same protocol.

## Transport

- Server command: `oppi-server --stdio` (normally launched through `oppi server --stdio --experimental`).
- Mirror dogfood smoke: `oppi runtime-loop smoke --json` starts `oppi-server --stdio`, creates a thread, records a Pi bridge event, runs an adapter-backed `turn/run-agentic` with multiple Pi tool results, exercises approval resume, cancellation, tool/result pairing error handling, continuation guard abort, and a long `memory/compact` handoff event, reads events/debug metrics, reports per-scenario results plus `bridgeClean` / `bridgeCleanReason`, and shuts the server down.
- Direct-worker smoke: `oppi runtime-worker smoke --json` starts a local mock OpenAI-compatible HTTP endpoint plus `oppi-server --stdio`, runs `turn/run-agentic` with `modelProvider.kind = "openai-compatible"` and `stream: true`, verifies Rust made authorized streamed provider requests, executes a provider-requested Rust tool, continues the provider turn with a `role=tool` result, observes streamed assistant deltas, reads events/debug metrics, reports `workerClean` / `workerCleanReason`, and shuts the server down. It does not require external provider credentials.
- Direct-worker product dogfood: `oppi runtime-worker [run] <prompt>` starts the same stdio server, creates a Rust thread, calls the OpenAI-compatible direct-provider path, prints assistant/tool/event/memory/todo diagnostics, and keeps stable Pi fallback guidance visible when provider auth or `oppi-server` is unavailable. Provider options include `--model`, `--base-url`, `--api-key-env`, `--system`, `--max-output-tokens`, `--no-stream`, `--prompt-variant off|a|b|caveman`, and the explicit dogfood-only approval helper `--auto-approve` / `--approve-all`. Hoppi memory is enabled by default for real provider runs when memory settings allow it; use `--memory`, `--no-memory`, or `OPPI_RUNTIME_WORKER_MEMORY=auto|on|off` to override per run. The TypeScript direct-worker wrapper now uses the spawned Rust server's `memory/backend/status`, `memory/backend/recall`, and `memory/backend/remember` routes for memory status, bounded recall injection, and bounded turn-summary writes instead of importing a CLI-hosted Hoppi backend. Native shell `/memory on|off`, `/memory startup-recall <on|off>`, `/memory task-start-recall <on|off>`, `/memory turn-summaries <on|off>`, `/memory agent-model <auto|claude|gpt>`, `/memory deep-model <auto|sonnet|gpt-5.5>`, `/memory idle-dream <on|off>`, `/memory install-offer <ask|dismissed>`, and `/memory sync ...` persist the same shared `oppi.memory` settings. Native shell memory operations also request runtime-owned `memory/backend/*` execution for bounded startup/task recall injection, bounded normal-turn summary writes, `/exit` full-session recap writes before shutdown sync, `/clear` / `/reset` clear-session recaps, dashboard/list/record mutations, maintenance, idle consolidation, and sync; the server backend runner owns the bounded Hoppi adapter and normalizes returned data through the existing `memory/*` cache/status routes. The detailed sync commands cover `repo`, `remote`, `pull-startup`, `push-exit`, `background`, `encryption`, `passphrase-env`, `passphrase-file`, and `conflict`, and write the shared `oppi.memory.sync` metadata with fixed `provider: "github"`. Explicit `/memory sync now|pull|push`, configured startup pull, shutdown/clear push, and background sync call `memory/backend/sync`, preserving repo/remote/conflict/passphrase/message options and rebuilding embeddings when pull/both sync asks for it. Native shell `/memory install-hoppi` shows explicit npm/network approval guidance and `/memory install-hoppi --yes` installs or updates `@oppiai/hoppi-memory` in OPPi's managed package directory; interactive native startup now also offers the same explicit yes/no install path when Memory is on, `hoppiInstallOffer` is `ask`, and no env/managed/legacy/local Hoppi backend module is present. Install/settings plumbing is client-owned and explicit; backend execution is the `memory/backend/*` JSON-RPC family. The prompt variant follows the same selection semantics as Pi (`--prompt-variant`, `OPPI_SYSTEM_PROMPT_VARIANT`, then stored `oppi.promptVariant`) and appends `promptname_a` or `promptname_b` to the direct-provider system prompt. Native/client hosts can pass `OPPI_RUNTIME_WORKER_FOLLOW_UP_JSON` in the direct-worker CLI path, or the JSON-RPC `followUp` field directly, so Rust owns the hidden follow-up prompt append while clients own busy-Enter queue UI.

- Request shape:

```json
{"jsonrpc":"2.0","id":"request-id","method":"initialize","params":{"clientName":"client"}}
```

- Response success shape:

```json
{"jsonrpc":"2.0","id":"request-id","result":{}}
```

- Response error shape:

```json
{"jsonrpc":"2.0","id":"request-id","error":{"code":-32000,"message":"...","data":{"code":"thread_not_found","category":"not_found"}}}
```

## Authentication

`initialize` is always allowed. When `OPPI_SERVER_AUTH_TOKEN` is set, all other methods must include `authToken` in `params` with an exact token match.

Executable/sensitive sandbox methods (`sandbox/exec`, `sandbox/windows-wfp-install`) require `OPPI_SERVER_AUTH_TOKEN` to be configured and fail closed when it is absent.

## Initialization and compatibility

### `initialize`

Params:

```ts
type InitializeParams = {
  clientName: string;
  clientVersion?: string;
  protocolVersion?: string;
  clientCapabilities?: string[];
};
```

Result:

```ts
type InitializeResult = {
  protocolVersion: string;
  minProtocolVersion: string;
  protocolCompatible: boolean;
  serverName: "oppi-server";
  serverVersion: string;
  serverCapabilities: string[];
  acceptedClientCapabilities: string[];
};
```

Compatibility rule: old clients may omit `protocolVersion`; otherwise, the client major version must match the server major version and the client minor version must be within the server's supported min/current range.

## Error taxonomy

JSON-RPC protocol errors use standard JSON-RPC numeric codes where practical:

| Code | Meaning |
| ---: | --- |
| `-32700` | parse error |
| `-32601` | method not found |
| `-32602` | invalid params |
| `-32000` | runtime error |
| `-32001` | authentication required |
| `-32020` | Windows WFP install failed |

Runtime errors expose stable machine-readable data:

```ts
type RuntimeErrorData = {
  code: string;
  category:
    | "not_found"
    | "already_exists"
    | "already_resolved"
    | "ownership_mismatch"
    | "terminal_state"
    | "approval_required"
    | "tool_pairing"
    | "event_store"
    | "provider"
    | "invalid_request";
};
```

Specific `code` values are stable within a category, for example `thread_not_found`, `approval_thread_mismatch`, `turn_not_mutable`, and `tool_pairing_error`.

## Core methods

Server lifecycle/observability methods:

- `server/shutdown` — acknowledge shutdown and let the stdio server exit after the response is flushed.
- `runtime/metrics` — return redaction-safe runtime counters for threads, turns, events, approvals/questions, plugins, MCP, models, and agents.
- `debug/bundle` — return a redacted debug bundle with runtime metrics and diagnostics suitable for support triage.

Thread/session methods:

- `thread/start` — create a thread for a project.
- `thread/resume` — resume an existing thread by `threadId`.
- `thread/fork` — fork a thread with an optional title.
- `thread/item-fork` — fork a new active child thread from a completed transcript item by `{ threadId, eventId, title? }`. The runtime validates the selected item, emits replayable `threadForkPointSet`, reports `branch.forkEventId`, and builds child provider history from the parent only through the selected event before adding child-thread history.
- `thread/item-edit-fork` — fork a new active child thread from a completed user-message item by `{ threadId, eventId, input, title? }`. The runtime validates that the selected item is a user message, returns the normalized replacement `input`, emits replayable `threadForkPointSet` with `historyCutoffEventId`, reports `branch.forkEventId` as the edited source item, and builds child provider history from the parent only before the original user item so the replacement turn is not preceded by the stale prompt.
- `thread/items` — list completed transcript items for a thread with optional `filter` (`default`, `no-tools`, `user-only`, `labeled-only`, or `all`), `after` event cursor, and bounded `limit` (default `1000`, max `5000`). Default/no-tools hide tool call/result items; labeled-only returns entries with runtime-owned labels. Results include `branch` metadata (`threadId`, `parentThreadId`, `forkEventId`, `childThreadIds`, `siblingThreadIds`, root-to-current `path`, and `depth`), compatibility `items`, and `entries[]` with each completed item's `eventId`, filter-relative `parentEventId`, `childEventIds`, `completedAtMs`, and `labels`, giving clients stable branch context, anchors, parent/child links, labels, and timestamps for point-in-history navigation without polling raw `events/list`.
- `thread/item-labels/set` — update replayable labels for a completed transcript item by `{ threadId, eventId, labels }`. Empty labels clear the item. The route returns `{ threadId, eventId, labels, events }` and emits `threadItemLabelsUpdated` with `targetEventId`.
- `thread/goal/get` — return the current goal for a thread, or `null` when none is set.
- `thread/goal/set` — create or update runtime-owned goal state for a thread. `objective` starts or replaces a logical goal; `status` may be `active`, `paused`, `budgetLimited`, or `complete`; `tokenBudget` sets a positive token budget or clears it when `null`.
- `thread/goal/clear` — remove the current goal for a thread and emit a goal-cleared event only when a goal existed.
- `thread/goal/continuation` — claim the next automatic goal continuation prompt for an active thread goal. The runtime increments the goal-continuation counter, returns the rendered continuation prompt while under `maxContinuations`, and pauses the goal with a `blockedReason` when the guard is exceeded.
- `events/list` — list events after an optional cursor with an optional bounded `limit` (default `1000`, max `5000`).

Goal state emits `threadGoalUpdated` and `threadGoalCleared` events. Active goals accumulate wall-clock seconds while Rust-owned agentic turns run. Direct-provider token accounting only uses provider-reported usage (`usage.total_tokens`, or Codex Responses `input_tokens + output_tokens` when no total is present); when usage is absent, token delta is `0` rather than guessed from text length. Crossing a positive token budget moves an active goal to `budgetLimited`.

Turn methods:

- `turn/start` — start a turn and emit the current 11-phase skeleton events.
- `thread/list` — returns persisted/replayed threads for native clients. `oppi-shell` uses it for `/tree`, together with existing `thread/start`, `thread/resume`, `thread/fork`, `thread/item-fork`, `thread/item-edit-fork`, and `thread/items`.
- `turn/run-agentic` — experimental Rust-owned 11-phase loop driver using scripted, adapter-backed, or direct-provider model steps, streaming assistant deltas, per-turn tool definitions, registered/sandboxed tool execution, adapter-provided tool results, bounded continuations, cancellation seams, hook diagnostics, and approval pauses.
- `turn/resume-agentic` — resume an approval-paused or user-input-paused Rust-owned agentic turn with approved tool-call ids or `askUserResponse`, optional per-turn tool definitions, cancellation settings, and continuation model steps.
- `turn/steer` — append steering input to a mutable turn.
- `turn/interrupt` — abort/interruption event for a mutable turn, including approval-paused agentic turns and running background turns. When a background turn owns the runtime lock, the server records a shared interrupt request and waits briefly for the running loop to emit `turnInterrupted`; clients can keep polling `events/list` if the interrupt is still pending at a long provider/tool checkpoint.

Agentic turn params now accept:

- `executionMode` — optional turn execution mode. Omitted/`blocking` preserves the existing request/response behavior. `background` is the first Plan 101 native-shell unblocker: `oppi-server --stdio` returns after the turn has started, mirrors semantic events into a server-side event stream, and lets clients poll `events/list` for live `TurnStarted`, phase, delta, tool, approval/question, completion, interrupt, or abort events while the background worker continues. Same-process approval/question resumes preserve direct-provider transcript snapshots. Across server restarts, the event store replays visible thread/turn/event state and aborts incomplete turns with a restart reason; durable direct-provider transcript replay is explicitly deferred. This is intentionally experimental; the stable blocking path remains the default.
- `followUp` — optional hidden follow-up chain metadata supplied by a host/client when a prompt was queued while an earlier answer was running. Rust appends the private follow-up routing guidance to direct-provider system prompts and emits only a redaction-safe diagnostic (`component=follow-up`, chain id, pending count). Native TUI/VS Code clients still own key routing, queue display, and queued-message restore.
- `sandboxPolicy` — optional turn-level Rust permission/sandbox policy. The direct-worker CLI maps `OPPI_RUNTIME_WORKER_PERMISSION_MODE` or stored `oppi.permissionMode` (`read-only`, `default`, `auto-review`, `full-access`) into this field, and native shell clients include Pi-compatible sandbox settings from `oppi.permissions.sandbox`: `projectRoots`, `readableRoots`, `writableRoots`, `allowInternet`, `allowSsh`, and extra protected patterns from `protectedPatterns`. `projectRoots` defaults to the current cwd when unset; read/write roots default to project roots when unset; read-only mode still sends an empty `writableRoots` list. `allowInternet` or `allowSsh` enables the turn-level network policy for future native shell turns and `/btw` side questions, matching the current Pi shell-tool mapping where either flag means network-enabled sandbox execution. Rust-owned shell/file tools use the turn policy when a tool call does not provide a narrower policy. Read-only mode blocks writes even if a write tool call was approved.
- `askUserResponse` on `turn/resume-agentic` — structured answers for an earlier `oppi__ask_user` tool call.   `apiKeyEnv` names an environment variable visible to `oppi-server`; raw API keys should not be sent over JSON-RPC. If omitted, OPPi checks `OPPI_OPENAI_API_KEY` then `OPENAI_API_KEY`. Explicit `apiKeyEnv` names fail closed unless they are `OPPI_OPENAI_API_KEY`, `OPENAI_API_KEY`, or an `OPPI_*_API_KEY` / OpenAI API-key-shaped variable; this prevents a compromised client from asking the server to read arbitrary environment variables and forward them to a provider endpoint. `kind: "openai-codex"` uses the protected `openai-codex` OAuth credential from the OPPi/Pi auth store (`OPPI_OPENAI_CODEX_AUTH_PATH` override, otherwise `OPPI_AGENT_DIR`/`PI_CODING_AGENT_DIR` `auth.json`) and never accepts raw tokens over JSON-RPC. `kind: "github-copilot"` uses the protected `github-copilot` OAuth credential from the same auth store (`OPPI_GITHUB_COPILOT_AUTH_PATH` override supported), refreshes through GitHub Copilot's token endpoint under the auth-store lock, and applies Pi/Copilot chat headers. `reasoningEffort` is optional and is forwarded to OpenAI-compatible providers as `reasoning_effort` and to Codex responses as `reasoning.effort` when not `off`; the CLI maps `/effort`-style `xhigh` to OpenAI-compatible `high` until provider-specific max-effort mapping lands. `modelProvider` cannot be combined with scripted `modelSteps`. When `stream` is true, provider SSE content chunks become separate assistant `ItemDelta` events and streamed function-call fragments are assembled before execution. Provider requests seed the configured system prompt plus compact runtime history from completed user/assistant items and the latest handoff summary. In the native shell direct-provider and `oppi runtime-worker` paths, the selected prompt variant is appended before memory, then bounded Hoppi startup/task recall comes from `memory/backend/recall`; the client appends the returned runtime-normalized context to `modelProvider.systemPrompt` and writes bounded turn summaries through `memory/backend/remember`. Provider diagnostics record redacted endpoint origin, status, duration, stream/chunk/tool/history counts, known provider token usage when supplied, and appear in `debug/bundle`. When `toolDefinitions` or built-in Rust tools are available, OPPi sends broad function schemas, maps provider tool calls back to Rust `ToolCall` events, appends one tool/function result per executed call, and continues the provider turn. Precise per-tool JSON schemas and durable provider/profile storage remain follow-up direct-worker slices. The native shell now has redacted `/provider validate` and opt-in `/provider smoke` for live OpenAI-compatible, Codex, Copilot, and explicit Meridian validation.
- `toolDefinitions` — per-turn tool definitions, used by the Rust registry to validate Pi/adapter tools without registering them globally and advertised to direct providers as available function tools.
- `cancellation` — deterministic cancellation seam (`beforeModelContinuation` or `toolCallIds`) that records aborted tool/turn events.

Agent and side-question methods:

- `agents/register` — legacy in-memory registration route with params `{ threadId, agent }`, where `agent` is an `AgentDefinition`. Filesystem-backed clients should prefer `agents/create` or `agents/update` so definitions are durable markdown files.
- `agents/list` — params `AgentListParams { threadId? }`; returns `AgentListResult { items, failed }`. Each `items[]` entry is `ResolvedAgent { active, shadowed[] }`, where `active` is the winning `AgentDefinition` and `shadowed` contains lower-priority definitions with the same name. `failed[]` contains `{ path, source, message }` for invalid markdown files. With a thread id, Rust loads built-ins plus project/user OPPi agent files and Claude-compatible agent files from the thread workspace.
- `agents/show` — params `AgentShowParams { threadId, name }`; returns one `ResolvedAgent` with the active definition and any shadowed definitions.
- `agents/create` — params `AgentWriteParams { threadId, source, definition, overwrite? }`; writes a durable markdown `AgentDefinition` and returns the written `AgentDefinition`. Writable sources are `project` and `user`.
- `agents/update` — params `AgentWriteParams { threadId, source, definition, overwrite? }`; updates a durable markdown `AgentDefinition` and returns the written `AgentDefinition`. Writable sources are `project` and `user`.
- `agents/delete` — params `AgentDeleteParams { threadId, source, name }`; deletes a writable project/user OPPi markdown definition and returns an empty object. Built-in, plugin, CLI, managed-policy, and Claude-compatible sources are read-only and fail closed.
- `agents/dispatch` — params `AgentDispatchParams { threadId, agentName, task, worktreeRoot?, background?, role?, model?, effort?, permissionMode?, memoryMode?, toolAllowlist?, toolDenylist?, isolation?, color?, skills?, maxTurns? }`; returns `AgentDispatchResult { run, events }`. - `agents/poll` — params `AgentRunPollParams { threadId, runId }`; returns `AgentRunPollResult { run, events, output? }`. Polling can drain a pending background AgentTool child request and returns the latest run status.
- `agents/resume` — params `AgentRunResumeParams { threadId, runId, followUp?, askUserResponse?, sandboxPolicy?, modelSteps?, modelProvider?, approvedToolCallIds?, cancellation?, maxContinuations? }`; returns `AgentRunPollResult { run, events, output? }` after routing approval or user-input responses back into a blocked background child turn.
- `agents/block` — params `{ threadId, runId, reason }`; marks a run blocked and returns `{ run, events }`.
- `agents/complete` — params `{ threadId, runId, output }`; marks a run completed and returns `{ run, events }`.
- `side-question/ask` — params `SideQuestionParams { threadId, question, parentTurnId?, executionMode?, sandboxPolicy?, modelSteps?, modelProvider?, toolDefinitions?, approvedToolCallIds?, cancellation?, maxContinuations? }`; returns `SideQuestionResult { answer, parentThreadId, sideThreadId, sideTurnId?, status?, events }`. Blocking `/btw` calls create a side thread titled from the question, run the scripted or provider-backed agentic turn there, emit a linked `sideQuestionAnswered` lifecycle event on the parent thread, and do not append user/assistant transcript items to the parent thread.

`AgentDefinition` is the durable markdown-facing agent shape: `{ name, description, source?, tools?, toolDenylist?, model?, effort?, permissionMode?, memoryMode?, background?, worktreeRoot?, isolation?, color?, skills?, maxTurns?, path?, filename?, readOnly?, instructions }`. Sources include `builtIn`, `claudeUser`, `user`, `claudeProject`, `project`, `plugin`, `cli`, and `managedPolicy`. Project `.oppi/agents/*.md` and user `OPPI_HOME/oppi/agents/*.md` definitions are writable. Project/user `.claude/agents/*.md` files are read-only compatibility imports, so native clients can list and show them but must not create, update, or delete them through OPPi.

`AgentRun` includes the run id, parent/child linkage, execution identity, policy metadata, and status: `{ id, threadId, parentThreadId?, childThreadId?, childTurnId?, agentName, status, task, worktreeRoot?, executionRoot?, background?, role?, model?, effort?, permissionMode?, memoryMode?, toolAllowlist?, toolDenylist?, isolation?, color?, skills?, maxTurns? }`. Status values are `running`, `blocked`, `completed`, and `failed`. Provider-backed `AgentTool` runs use a child thread; when `worktreeRoot` is set, `executionRoot` is the resolved child root and child readable/writable sandbox roots are scoped there.

- `memory/status` — returns the current Rust-held `MemoryStatus`. The status keeps Hoppi-style fields when a client/backend supplies them: `{ enabled, initialized?, backend, scope, storePath?, projectId?, memoryCount, pinnedCount?, lastWriteAt?, lastConsolidatedAt?, queueDepth?, dashboardUrl?, executionOwner?, executionAdapter?, executionAdapterKind? }`. Runtime-owned backend routes annotate status with `executionOwner: "runtime"`, the adapter id, and the adapter kind when known, while direct `memory/set` clients may omit those fields. `queueDepth` is refreshed from active `memory/jobs/update` records when the reported-job ledger is used.

- `memory/jobs/update` — params `{ threadId, jobId?, kind, status, stage?, source?, message?, queuedAt?, startedAt?, finishedAt?, recordCount?, deletedCount?, dryRun?, backendApplied?, agentModel?, deepModel?, modelUsed? }`; creates or updates a reported Hoppi memory job in Rust. Job `kind` values include `recall`, `remember`, `consolidate`, `sync`, `dashboard`, `list`, `recordMutation`, and `compact`; statuses are `queued`, `running`, `succeeded`, `failed`, `skipped`, and `cancelled`. Queued/running jobs count toward `MemoryStatus.queueDepth`, updates emit `MemoryJobUpdated`, and the response is `{ status, queueDepth, totalCount, items, message, controls?, diagnostics?, events? }`. Job items preserve the optional model fields, and runtime-owned `memory/backend/consolidate` uses them to show requested `agentModel` / `deepModel` and backend-reported `modelUsed` for visible maintenance/deep-dream work. Runtime-owned `memory/backend/*` executions use this ledger for visible running and terminal state; standalone host clients can still use the route for externally owned work.
- `memory/jobs/cancel` — params `{ threadId, jobId, reason?, finishedAt? }`; marks an active reported Hoppi memory job as `cancelled`, preserves kind/stage/source/count metadata, refreshes `MemoryStatus.queueDepth`, emits `MemoryJobUpdated`, and returns the same jobs result shape. Runtime-owned backend and distiller terminal updates preserve an already-cancelled job instead of overwriting it as succeeded/failed; returned backend execution results and distill-turn results report `cancelled: true` when that terminal state is observed. This is a runtime ledger/host-control signal; process interruption still depends on the backend runner or provider boundary.
- `memory/jobs/list` — params `{ threadId?, limit?, includeFinished? }`; returns `{ status, queueDepth, totalCount, items, message, controls?, diagnostics?, events? }` for the current reported-job ledger. By default it shows active queued/running jobs; pass `includeFinished: true` to include recent succeeded/failed/skipped/cancelled jobs. Limits are capped at 500.

Each route validates the thread, starts a visible memory job, calls the configured server backend runner, normalizes backend output through the existing Rust `memory/*` cache/status routes, records terminal job state, and returns `MemoryBackendExecutionResult { jobId, requestId?, operation, normalized, backend, adapterKind?, summary?, timedOut, timeoutMs?, cancelled, diagnostics }`. Backend runners also expose `MemoryBackendAdapterInfo { id, kind, embedded, operations, diagnostics }` internally using the full operation catalog, but there is no separate public adapter-info route yet. `OPPI_MEMORY_BACKEND=auto|node|embedded` selects the runner: `auto` and `node` keep the bounded Node adapter discovery path, while `embedded` opens the Rust local store at `OPPI_HOME/memory/embedded-memory.json` and supports status, remember, recall, list, forget, pin/unpin, update, and supersede through the same normalization boundary. Embedded dashboard startup currently returns `memory_backend_embedded_operation_unavailable`, and embedded consolidate/sync return visible normalized no-op results by RC decision; dashboard UI, embeddings, remote sync, richer search, and Rust-owned deep maintenance are deferred. Backend-supplied status normalized through these routes is annotated with `executionOwner: "runtime"`, `executionAdapter: <runner backend id>`, and `executionAdapterKind` when the backend supplies it or the runner reports one. The default server runner still uses a bounded Node adapter for the installed Hoppi package, reports `adapterKind: "node-typescript"`, and advertises `embedded: false`; explicit embedded results report `adapterKind: "rust-embedded"` and `backend: "hoppi-embedded"`. On Node timeout the server kills the child process, returns a provider error with code `memory_backend_node_timeout`, records the memory job as `failed`, and refreshes queue depth to zero. Hoppi package installation remains an explicit client action through `/memory install-hoppi`, first-start install prompts, or `oppi mem install`; no backend route runs npm/package-manager work.

## Runtime-loop dogfood modes

Plan 22 uses this config shape for dogfooding the Rust loop without breaking stable Pi usage. The smoke command now reports a `scenarios` array for dry-run hardening coverage (`bridge-smoke`, `approval-resume`, `cancellation`, `pairing-error`, `guard-abort`, and `long-compaction`):

- `default-with-fallback` (default) — automatically mirror normal Pi turns into Rust while keeping Pi as the primary runtime and visible fallback if `oppi-server` is unavailable.
- `command` — keep normal Pi runtime behavior; `/runtime-loop <prompt>` opt-in mirrors a single Pi turn into Rust.
- `OPPI_RUNTIME_LOOP_MODE=off` or `oppi.runtimeLoop.mode = "off"` — disable `/runtime-loop` mirroring.

`oppi doctor` reports the selected runtime-loop mode, direct-worker readiness, and native Rust shell readiness separately, then suggests `oppi runtime-loop smoke --json` / `oppi runtime-worker smoke --json` when the experimental runtime is unavailable or provider auth is missing. Plan 22's repeated smoke passes and follow-up sanity audit promoted `default-with-fallback` to OPPi's default while keeping stable Pi execution as the primary/fallback path. Plan 23 adds `oppi runtime-worker smoke --json` as the direct-provider regression gate and `oppi runtime-worker <prompt>` as the opt-in product dogfood/default-candidate command: the smoke uses a local mock provider, so a clean result means Rust owned the streamed provider HTTP request/tool-continuation path, not that an external account/model was validated. Plan 24 starts parity by preserving Hoppi in that direct-worker path, then adds prompt A/B overlays, `todo_write`/`todos/list`, follow-up prompt routing, provider env safety, todo-aware `memory/compact` details, turn-level `sandboxPolicy`, `ask_user`, `suggest_next_message`, feedback drafts, `render_mermaid`, initial `shell_task`, host-adapter-first `image_gen` safety, and command prompt expansion for review/audit/init/independent/feedback; remaining slash commands/tools are being ported one at a time.

## Stability notes

- The contract is experimental, but clients should treat `initialize.protocolCompatible=false` as a warning/blocking condition before using advanced methods.
- Runtime invariants reject cross-thread mutations, late terminal-turn mutation, duplicate approval/question resolution, and malformed tool batches before partial mutation.
- Sandbox execution must fail closed when a policy requires OS enforcement that the current platform cannot provide.
- Future stable clients should prefer generated TypeScript types from Rust protocol schemas once the generation pipeline lands.
